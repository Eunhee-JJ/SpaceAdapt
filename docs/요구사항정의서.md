# SpaceAdapt 요구사항 정의서 (v3)

> 관련 문서: [구현계획.md](구현계획.md) · [SpaceAdapt_프로젝트소개서.html](SpaceAdapt_프로젝트소개서.html)
>
> v3 변경: 구현 계획을 별도 문서로 분리. VLM 역할을 "가구 인식"에서 "생활 단서 추출"로 재정의(FR-05, P-8). 기능 요구사항 번호 재정렬.

## 1. 문서 목적

작은 주거 공간에서 여러 생활 활동을 수행하는 사용자를 위해, 방과 가구를 2D 공간 모델로 구성하고 실행 가능한 가구 배치안을 제안하는 SpaceAdapt MVP의 요구사항과 범위를 정의한다. 일정·담당·관문은 [구현계획.md](구현계획.md)에서 다룬다.

## 2. 서비스 개요

### 2.1 문제

원룸·기숙사 등 제한된 공간에서는 수면, 학습, 재택근무, 취미 활동이 서로 간섭한다. 사용자는 불편의 원인과 가구 재배치 우선순위를 스스로 파악하기 어렵고, 일반 인테리어 추천은 실제 치수·동선·문 개폐·가구 사용 공간을 충분히 반영하지 못한다.

### 2.2 해결 방식

사용자가 방 사진을 올리면(또는 지원 기기에서 RoomPlan 스캔 결과를 가져오면) 시스템은 방 구조와 가구의 2D 모델 초안을 만들고, VLM이 사진 속 생활 흔적에서 활동·불편 단서를 추출한다. 에이전트는 단서를 가설로 삼아 확인 질문으로 생활 우선순위를 정한다. 공간 플래너는 물리 제약과 활동 영역 간섭을 검사한 배치안 2개를 생성하고, 사용자는 모바일에서 비교·수정·재검증한다.

### 2.3 AI 역할 원칙

| 구성 | 담당 | 비고 |
| --- | --- | --- |
| 사용자 입력 · RoomPlan | 기하: 어디에, 얼마나 큰가 | 치수의 확정 출처 |
| VLM | 의미: 방이 어떻게 쓰이고 있는가 | 생활 흔적·가구 속성 추출, 추정값만 생성 |
| LLM 에이전트 | 단서 → 가설 → 확인 질문 → 가중치·제약 | 질문 선택과 답변 구조화 |
| 공간 플래너(비AI) | 배치 생성·검증 | 결정적 계산, 제약 보장 |

### 2.4 핵심 원칙

- 사진·VLM·스캔 결과는 **초안**이며, 실측 정답으로 취급하지 않는다.
- 최종 배치 계산은 사용자가 확정(`confirmed`)한 치수와 좌표를 기준으로 한다.
- AI 추정은 단정하지 않고 확인형 질문으로 사용자에게 검증받는다.
- 결과는 이미지가 아니라 수정·검증 가능한 2D 공간 모델이다.
- 모든 입력 경로는 동일한 2D 공간 모델로 정규화한다.
- 외부 AI·기기 기능이 실패해도 수동 입력으로 전체 흐름을 완료할 수 있어야 한다.

## 3. 대상 사용자와 가치

| 구분 | 정의 |
| --- | --- |
| 주요 사용자 | 원룸·기숙사에서 생활하는 청년 1인 가구(대학생, 취업준비생, 재택·하이브리드 근무 사회초년생) |
| 보조 사용자 | 입주 전 배치를 고민하는 예비 자취생, (확장) 기숙사·셰어하우스 운영자 |
| 사용 상황 | 수면·업무·학습·취미가 한 방에서 충돌할 때 |
| 사용자 가치 | 불편을 몰라도 시작, 사지 않고 기존 가구로 개선, 옮기기 전에 검증 |

## 4. 범위

### 4.1 MVP 핵심 범위 (필수)

1. 방·가구·고정 구조물 2D 모델 생성 및 편집
2. 방 크기, 문·창문, 가구 크기·위치·회전 보정
3. 사진 → VLM 가구 목록·대략 위치·생활 단서 초안
4. 생활 단서 기반 확인 질문 2~3개
5. 배치 후보 2개 생성
6. 가구 충돌, 가구 사용 공간, 문 개폐, 통로 폭, 고정 구조물 침범, 활동 영역 간섭 검증
7. 후보별 점수·위반·이동 가구 수·이동 비용 비교
8. 가구 직접 이동 후 즉시 재검증
9. 선택 배치안 실행 가이드(이동 순서)

### 4.2 스트레치 범위 (조건부)

| 항목 | 착수 조건 |
| --- | --- |
| iOS RoomPlan 스캔 JSON 가져오기(FR-12) | [구현계획.md](구현계획.md) D4 관문 통과 |

### 4.3 MVP 제외 범위

- PWA 내장 AR 스캔(ARCore Depth, WebXR 포함)
- 다중 프레임/영상 기반 깊이 추정
- 단일 사진만으로 보장되는 실측 정확도 및 이미지 좌표→cm 자동 환산
- 전체 3D 렌더링 또는 AR 배치 미리보기
- 미닫이·접이식 문
- 얼굴 자동 블러(데모는 합성·허가 자료만 사용)
- 가구 구매·배송·시공 연계
- 실제 사용자 대규모 성능 검증

## 5. 사용자 흐름

```text
입력 선택
  ├─ 사진 업로드 → VLM 가구 목록·대략 위치·생활 단서
  ├─ (스트레치) RoomPlan JSON 업로드 → 벽·문·창·가구 치수 초안
  └─ 수동 입력
  → 2D 편집기에서 치수·위치·문/창문·고정 구조물 확정
  → 생활 단서 기반 확인 질문 2~3개
  → 배치안 2개 생성
  → 제약 충족 여부·점수 비교
  → 선택안 터치 편집 → 즉시 재검증
  → 실행 가이드 확인
```

## 6. 기능 요구사항

### FR-01. 공간 입력

- 사용자는 사진 업로드, 수동 입력, (스트레치) RoomPlan JSON 업로드 중 하나로 방을 등록할 수 있어야 한다.
- 시스템은 입력 방식과 무관하게 §8의 동일한 2D 공간 모델로 정규화해야 한다.
- 모든 입력 경로에서 방 치수, 문·창문, 고정 구조물을 수정할 수 있어야 한다.

### FR-02. 방 구조 모델

- 방은 벽을 잇는 2D 폴리곤으로 표현한다. MVP 편집 UI는 사각형 방을 기본으로 하되, RoomPlan 가져오기 결과는 폴리곤을 그대로 유지한다.
- 문과 창문은 벽 인덱스와 벽 시작점 기준 오프셋으로 저장한다.
- 문은 폭, 경첩 위치(`hinge: left|right`), 열림 방향(`swing: in|out`)을 저장한다. 문 회전 영역은 폭을 반지름으로 하는 사분원으로 계산한다.
- 창문은 폭과 하단 높이(`sillHeight`)를 저장한다. 하단 높이보다 낮은 가구는 창 앞 배치를 허용한다.
- 싱크대·주방 상판·붙박이장·보일러실 등 이동 불가 구조물은 `fixtures`로 저장한다.

### FR-03. 가구 모델

- MVP 가구 클래스는 침대, 책상, 의자, 수납장, 테이블, 소파, 옷장/행거, 냉장고 8종으로 한다.
- 각 가구는 유형, 가로·세로·높이, 이동 가능 여부, 속성, 필드별 확정 상태를 가진다. 위치는 배치(layout)별로 분리 저장한다.
- 가구 평면 형상은 회전 직사각형(OBB)으로 표현한다.
- 각 가구는 유형별 기본 사용 여유공간(`clearance`)을 가진다(§10.4).
- 가구 속성(`attributes`): 접이식, 바퀴, 소파베드, 로프트 등. 이동 비용과 여유공간 계산에 반영한다.
- 추정값(`estimated`) 필드가 남은 가구가 있으면 배치 생성 전에 확인을 요구한다.

### FR-04. 치수 확정

- 사진 입력에서 VLM은 가구 유형, 개수, 벽 기준 대략 위치만 제공한다. 실제 cm 값은 사용자가 2D 편집기에서 확정한다.
- 사진 입력 시 방의 가로·세로 입력은 필수다. 가구 치수는 유형별 표준 치수를 기본값으로 채우고 `estimated`로 표시한다.
- RoomPlan 입력은 치수를 `estimated`로 가져오되, 사용자가 일괄 확정할 수 있다.
- 확정되지 않은 값은 UI에서 추정 상태로 구분해 표시한다.

### FR-05. 생활 단서 추출 (VLM)

- VLM은 사진에서 가구 외에 **생활 흔적**과 **가구 상태**를 추출해 `lifeCues`로 저장한다.

| 단서 유형 | 예 | 추정 대상 |
| --- | --- | --- |
| 활동 흔적 | 책상 위 모니터 2대, 침대 위 노트북, 바닥 요가매트·악기 | 활동 가중치(primaryActivity, hobbySpace) |
| 기능 전용·과부하 | 책상 위 물건 적치, 넘치는 행거 | 불편 가설(mainPain: 작업 공간 부족, 수납 부족) |
| 가구 속성 | 접이식, 바퀴, 소파베드, 로프트 침대 | `attributes`, `movable`, 이동 비용 |
| 원룸 특유 물건 | 빨래건조대, 바닥 매트리스, 전자레인지 선반 | 가구 클래스 매핑 또는 `other` |

- 각 단서는 근거 문장, 관련 객체, 추정 슬롯, 추정값, `status: estimated`를 가진다.
- 단서는 사용자 확인 전까지 가중치·제약에 반영하지 않는다. 확인 질문의 근거와 슬롯 초기값으로만 쓴다.
- VLM 실패 시 단서 없이 FR-06의 기본 질문 순서로 진행한다.

### FR-06. 요구 탐색

- 시스템은 최대 3개의 질문으로 활동 우선순위, 가장 큰 불편, 이동 불가 가구·제약을 확인한다.
- 질문은 고정 질문 뱅크(§10.5)에서 선택한다. 각 질문은 채울 슬롯과 슬롯→가중치/제약 매핑을 가진다.
- 생활 단서가 있는 슬롯은 근거를 제시하는 **확인형 질문**을 우선한다(예: "책상에 모니터가 2대 보여요. 재택근무를 자주 하시나요?").
- LLM은 아직 확정되지 않은 슬롯 중 배치 결과에 영향이 큰 질문을 고르고, 자유 답변을 슬롯 값으로 구조화한다.
- 이미 확보한 정보와 중복되는 질문은 하지 않는다.
- 동일한 슬롯 값은 항상 동일한 가중치·제약으로 변환된다(결정적 변환).

### FR-07. 활동 영역

- 시스템은 수면·업무·취미 활동 영역(`zones`)을 관련 가구의 사용면과 여유공간에서 자동 생성한다.
- 서로 다른 활동 영역이 겹치는 면적을 **활동 간섭**으로 계산한다.
- 사용자는 2D 화면에서 활동 영역과 간섭 구간을 시각적으로 확인할 수 있어야 한다.

### FR-08. 배치 생성

- 시스템은 서로 다른 특성의 배치안 2개를 생성한다: ① 선호 우선안(활동 가중치 최대 반영), ② 이동 최소안(기준 배치 대비 이동 비용 최소).
- 고정 가구와 고정 구조물은 이동하지 않는다.
- 플래너는 회전을 0/90/180/270도로 제한한다.
- 모든 후보는 기준 배치(`baselineLayout`)와 분리 저장하며, 제약 검사 결과와 함께 저장한다.

### FR-09. 제약 검증

- 가구 간 충돌, 가구와 벽·고정 구조물 충돌을 검사한다.
- 가구 여유공간과 다른 가구·구조물의 겹침을 검사한다.
- 문 회전 영역 침범을 검사한다.
- 통로 폭: 빈 공간(방 − 가구 − 고정 구조물)을 최소 통로 폭의 절반만큼 침식(buffer(−w/2))했을 때, 출입문에서 모든 가구의 사용면까지 연결되어야 한다.
- 각 위반은 대상 객체, 위치(폴리곤), 위반 유형, 사유 문장을 포함한다.

### FR-10. 결과 비교 및 편집

- 사용자는 2개 배치안과 기준 배치의 총점, 하드 위반 수, 활동 간섭 면적, 이동 가구 수, 이동 비용, 선호 충족률을 비교할 수 있어야 한다.
- 사용자는 가구를 드래그·회전(자유 각도)·크기 수정할 수 있어야 한다.
- 수정 뒤 제약 검증과 점수 계산이 다시 실행되어야 한다.

### FR-11. 실행 가이드

- 선택 배치안에 대해 가구별 이동 순서를 제공한다.
- 순서 규칙: 다른 가구의 목표 위치를 점유한 가구를 먼저 이동한다. 순환 의존이 있으면 임시 위치(빈 공간 중 가장 큰 영역)를 경유하도록 안내한다.
- 가구별 안내는 "어디에서 → 어디로, 회전 여부, 주의 사항(문 개폐·통로)" 템플릿 문장으로 제공한다.

### FR-12. RoomPlan 가져오기 (스트레치)

- iOS 최소 앱(Swift, RoomPlan, iOS 16+, LiDAR 기기)은 `CapturedRoom`을 JSON으로 내보낸다.
- 웹은 JSON을 업로드받아 변환기로 §8 모델을 생성한다.
  - 단위: m → cm
  - 좌표: 3D transform에서 바닥 평면(x, z)으로 투영, yaw만 회전각으로 사용
  - 벽 → 방 폴리곤, 문·창 → `openings`, 객체 → `furniture`
  - 클래스 매핑: bed→bed, table→table/desk(사용자 선택), chair→chair, sofa→sofa, storage→storage/wardrobe, refrigerator→fridge, sink·stove·oven·washerDryer→fixtures, 그 외→무시
  - 문 경첩·열림 방향은 RoomPlan이 제공하지 않으므로 사용자 확인 필수
- RoomPlan 입력에도 사진이 있으면 FR-05 생활 단서 추출을 함께 수행할 수 있다.
- 시연 장애에 대비해 사전 스캔 JSON 1개 이상을 데모 자료로 보관한다.

| NFR-03 | VLM/API 실패 시 수동 입력과 목 데이터로 데모를 계속할 수 있어야 한다. | VLM 비활성 상태 E2E |
| NFR-04 | 업로드 사진은 메모리에서만 처리하고 저장하지 않는다. 생활 단서는 사진이 아닌 텍스트로만 보관한다. | 서버 저장 경로 없음 확인 |
| NFR-05 | 데모는 합성·사용 허가 자료만 사용한다. VLM 제공사의 데이터 보관 정책을 확인해 기록한다. | 소개서 별첨 기재 |
| NFR-06 | 모든 AI·스캔 추정값은 사용자가 수정할 수 있어야 한다. | 편집기·질문 화면에서 수정 가능 |

## 8. 공간 데이터 모델

규약:

- 단위 cm. 원점은 방 폴리곤 좌상단, x는 오른쪽, y는 아래쪽.
- 가구 위치 `x`, `y`는 **중심 좌표**. `rotation`은 시계 방향 degree.
- 가구 `width`는 회전 0도 기준 x축 길이, `depth`는 y축 길이. 사용면(front)은 회전 0도에서 +y 방향.

- 이동 가능 여부의 단일 출처는 `furniture.movable`이다.

## 9. 기술 설계

```text
Vue 3 + Konva + PWA (Cloudflare Pages)
  └─ 업로드, 2D 편집기, 질문 UI, 비교·편집, 실행 가이드

FastAPI (Cloud Run, min-instances=1)
  └─ 세션, 공간 모델 API, VLM 어댑터(실/목), RoomPlan 변환기, 플래너 실행

LangGraph
  └─ VLM 결과 구조화(가구·생활 단서), 미확정 슬롯 식별, 확인 질문 선택, 답변→슬롯 구조화

Spatial Planner (Python)
  ├─ 후보 생성: OR-Tools CP-SAT (10cm 그리드, NoOverlap2D, 회전 4방향)
  ├─ 점수 계산: Python 함수 (§10.3)
  └─ 정밀 검증: Shapely (충돌·여유공간·문 회전·통로·간섭)

(스트레치) iOS RoomPlan Export 앱 (Swift)
  └─ 스캔 → CapturedRoom JSON 내보내기(공유 시트)
```

- 검증 로직은 Python 한 곳에만 둔다(클라이언트 중복 구현 금지). 편집 중 재검증은 300ms 디바운스 후 호출한다.

## 10. 배치 최적화 규칙

### 10.1 하드 제약

- 가구끼리 겹치지 않는다.
- 가구는 방 폴리곤 내부에 위치한다.
- 가구 여유공간은 다른 가구·고정 구조물과 겹치지 않는다(여유공간끼리 겹침은 허용).
- 문 회전 영역을 침범하지 않는다.
- 고정 구조물 영역을 침범하지 않는다.
- 최소 통로 폭 조건(FR-09)을 만족한다.
- 이동 불가 가구는 기준 배치 위치를 유지한다.

### 10.2 소프트 목표

- 우선 활동 영역의 유효 면적을 최대화한다.
- 활동 간섭 면적을 최소화한다(예: 수면 영역과 업무 영역 분리).
- 사용자 선호 슬롯 충족률을 최대화한다.
- 기준 배치 대비 이동 비용을 최소화한다.
- 하단 높이보다 높은 가구가 창을 가리지 않는다.

### 10.3 점수

```text
총점 = w_pref × 선호 충족률(0~1)
     + w_zone × Σ(활동 가중치 × 활동 영역 유효 면적 비율)
     + w_aisle × 통로 여유율
     − w_int × 활동 간섭 면적 비율
     − w_move × 이동 비용 정규화값

이동 비용 = Σ(이동 거리 m × 가구 유형 가중치) + 회전 가구 수 × 0.5
가구 유형 가중치: 침대·옷장·냉장고 3, 소파·수납장 2, 책상·테이블 1.5, 의자 0.5
속성 보정: 바퀴 ×0.5, 접이식 ×0.7
```

- 선호 우선안과 이동 최소안은 `w_*` 프로필만 다르다.
- 하드 위반 후보는 출력하지 않는다. 사용자 편집으로 생긴 위반은 점수 대신 위반 목록으로 표시한다.
